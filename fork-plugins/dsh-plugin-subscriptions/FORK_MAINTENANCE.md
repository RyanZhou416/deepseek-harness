# Subscriptions fork maintenance

This subtree carries the private `dsh-plugin-subscriptions` build shipped with this fork.

## Upstream and build identity

- Upstream repository: `https://github.com/V1ki/dsh-plugin-subscriptions.git`
- Upstream tag: `v0.9.4`
- Fork source candidate: `0.9.4-dsh021rc2.1` — the real Web profile links the staged build at `.build/fork-plugins/subscriptions`, not this checkout, so the running Host keeps executing its previous build until the Host is stopped, `build.cmd` is run, and the Host is restarted. The historical install state is recorded in [docs/claude-implementation-status.md](docs/claude-implementation-status.md).
- Subtree path: `fork-plugins/dsh-plugin-subscriptions`
- Distribution artifact: none — the profile installs the staged build through a `link:` dependency; the previous-generation tarballs live under `fork-plugins/releases/archive/` and must not be installed.

## Fork behavior

The fork keeps upstream provider, account, credential-store, request-translation, and tool names. It uses the RC.1 awaited `agent/created` payload and exact DSH dependency cohort. The V4 adapter maps first-class `role: 'tool'` messages to the existing provider translators' result blocks, preserving call id, failure flag, order, and image attachments; developer messages fail explicitly until a provider supports them. The independent test environment installs the UI primitive runtime dependencies that the Harness Web application normally supplies.

Each Node test process gets a private temporary `DSH_HOME` before plugin imports. Codex and Grok stream tests inject their fetch implementation through the adapter's existing option, so a developer's proxy configuration and credentials cannot redirect synthetic requests to real providers. Production routes still use the configured proxy.

The Session format version stays 4, and the Claude route writes one new required-on-read event, `llm/request-record`, whose recording service and reader must both be present in the Host that runs it; a Host without them withholds the Claude route instead of skipping the record. Existing Codex, Claude, Grok, Copilot, and Antigravity session objects otherwise keep their shape. Cursor adds fields; Claude gains two optional wire-identity fields, and credentials gain the ownership field the typed credential record already carries — those additions are not an "unchanged" claim. The private continuation-state documents are plugin state, not part of the Session structure or format. Existing subscription credentials remain owned by the plugin's configured DSH home and are not copied into this repository.

## Reapply after an upstream import

`V1ki/dsh-plugin-subscriptions` v0.9.4 does not contain the behaviors in this section. A subtree import overwrites `src/`, `test/`, and `package.json`. Restore every item here before packaging, then run the package suite and rebuild the tarball. The tests named below fail if the behavior was dropped.

### OAuth callback correlation

The loopback OAuth handler validates the callback path and the attempt's `state` before handling either an authorization code or a provider error. A callback with missing or mismatched state receives HTTP 400 and cannot settle the attempt. A matching provider error still rejects the login and releases its callback listener. Manual code entry retains its separate input rules.

**Preservation rule.** Keep state validation ahead of both `error` and `error_description`; do not let an uncorrelated rejection cancel another login attempt.

**Focused verification.** `test/oauth-flow.spec.ts` exercises the real callback listener on OS-assigned loopback ports with synthetic callbacks, including missing and mismatched state, a later matching callback, matching provider errors, and unrelated paths. No authorization or token endpoint is contacted.

### Advisory model resolution

Model selection and capability resolution answer from the account's last-known catalogue. A read never starts a provider request, however cold or stale the entry is: an account with nothing stored contributes its static rows, and logout and account allowlists remain current checks. Only the account a request is about to use ensures its own catalogue; the explicitly requested reads (opening **Manage**, the manual refresh) are the separate events that may query. Every account persists its own catalogue, so a restart serves each login's last-known plan rather than only the default account's.

Pool snapshots are scoped to the requested provider. Configured extra tier rows are read directly from configuration without discovering account catalogs; explicit cross-provider tiers remain owned by their first member's provider. Pool membership assembly uses the advisory account read, while request-time membership and quota checks remain separate.

**Preservation rule.** Keep advisory resolution separate from fresh stream validation, scope pool assembly by provider, and do not turn an unavailable advisory result into a second discovery attempt. Do not assemble account pools merely to enumerate configured tier rows, and do not let a capability, picker or ranking read start a provider request.

**Focused verification.** `test/catalog-resolution-cost.spec.ts` checks deferred refreshes, cold reads, provider isolation, logout, configured-tier enumeration and actual plugin wiring without remote requests. `test/pool.spec.ts` checks configured tier ownership and precedence. The performance assertions use request counts and held promises rather than elapsed-time thresholds.

### Demand-driven metadata caches

Catalogue and usage metadata are durable per-account caches under `DSH_HOME/plugins/subscriptions/`: `models.json` (layout version 2, one entry per provider ACCOUNT, a failure hint beside the last good snapshot) and `usage-cache.json` (normalized windows with their observation times, the plan, and a read cooldown; no token, request id or provider message). `src/cache-policy.ts` resolves `cache.modelMaxAgeMs` (24 h), `cache.usageMaxAgeMs` (5 min) and `cache.retryDelayMs` (60 s) as freshness and cooldown thresholds; no duration schedules work. `src/providers/catalog-store.ts` and `src/providers/usage-store.ts` own the files, `src/providers/provider-catalog.ts` and `src/providers/pool-usage.ts` are their readers, and `src/client/subscriptions-cache.ts` is the one browser-side cache the usage badge and the Settings page share.

Provider queries happen only on explicit events: a login refreshes that account's catalogue and no usage; opening **Manage** revalidates that provider's catalogues only where an entry is stale; **Edit model list → Refresh** forces every account's catalogue; opening the usage pill asks for an if-needed read of the current provider; the usage Refresh control forces one account's reading; a consumed Codex reset credit re-reads its account; the account a request is about to use ensures its own catalogue; and the pool candidate about to serve ensures its own catalogue and usage reading. A finished run, a window focus, a connection reset, a model switch, a login/logout roster change and the cache's seeding read for a new account are local reads (`readProvider` / `readAll` with mode `local`) and reach no provider. Pool ranking otherwise reads retained entries, so ranking never sweeps peer accounts. A failed read stores its cooldown — the provider's disclosed `retry-after` when there is one, else `cache.retryDelayMs` — in the same file, and `force` re-requests a fresh success without ever bypassing a live cooldown. `models.json` rows written before accounts were keyed are discarded rather than attributed, and a canonical-key rename moves the account's catalogue, usage reading, cooldowns, pool health and account preferences to the new key — whether the save announced it or the store only recorded the alias on an earlier run, which `src/providers/cache-identities.ts` reconciles from the store's own alias records once, before the model routes, speed, usage and providerSettings reads, and without any provider query.

The remaining timers are protocol or local: the login-progress poll while an authorization attempt is in flight (it also observes the Copilot device grant), the credential-store lock lease renewal, the open usage panel's countdown render, and the opt-in Claude Code keychain sync. The browser half re-reads locally on a finished run, a window focus, a new connection generation, a model switch and a roster change, and every one of those reads answers from the node half's cache.

**Preservation rule.** Keep every provider read on those events; add no interval, timer, or read path that refreshes peers. Keep the failure cooldown durable and unbypassable by `force`, keep the caches keyed by provider account, keep the load-time alias reconciliation ahead of the first account read, and keep the legacy-layout discard rather than guessing an owner.

Known limitation: an HTTP 403/404 that might mean a model was withdrawn does not trigger an automatic catalogue re-read, because no trustworthy machine-readable code separates that from an entitlement or endpoint refusal; recovery is a manual **Refresh** or the ordinary stale-demand re-read.

**Focused verification.** `test/cache-policy.spec.ts` pins the thresholds and rejects unusable durations. `test/cache-demand-rpc.spec.ts` mounts the real plugin and asserts that repeated listing, resolution, `providerSettings`, `usage` and `speed` reads contact no catalogue owner and no network, that a scoped `refresh` addresses only the requested provider, and that an ambiguous flag is rejected. `test/catalog-store.spec.ts`, the `usage store:` cases in `test/pool-usage.spec.ts` and `test/usage-cache.spec.ts` cover the two cache files and the browser half; `test/catalog-resolution-cost.spec.ts` and `test/pool-usage.spec.ts` cover an idle clock, `force` against a live cooldown, a cooldown outliving the process and a non-default account's catalogue surviving a reload; `test/account-rename.spec.ts` covers the rename follow-through and the stored-alias reconciliation at load; `test/subscription-client-runtime.spec.ts` mounts both client surfaces to prove no network timer is registered.

### One owner for the provider catalog and pool plumbing

The six adapters used to carry their own copy of the same catalog code: `clearAccountCatalog`
was byte-identical in all six, `catalogFor` and `listModels` in five, and `listOwnModels` was
near-identical with per-provider differences. They now delegate to `provider-catalog.ts`, which
owns the cache, the listing skeleton (account union, per-account bound, abort and credential
error mapping), the picker-row shape, and the pool-tier overlay. Per-provider differences stay
explicit: the discovery timeout hook, each adapter's modality rule and description, the warn
label's capitalisation, and grok's last-known short-circuit.

The account-pool delegation has the same single owner: `PoolBackedAdapter` in
`pool-delegation.ts` owns `listModels` (own rows plus configured tiers), `listOwnModels`,
`resolveModel`, the `stream` pool prelude, and `streamAccount`. An adapter keeps only its own
catalogue data, its model-field assembly (`resolveOwnModel`) and its wire path (`streamOwn`).
`clearAccountCatalog` stays per adapter because claude's also drops the account's uploaded File
ids.

A catalogue entry the provider marks disabled stays listed, and its reason travels all the way to
the surfaces that offer the row: `modelDisabledReason` in `provider-catalog.ts` reads the extension
the adapters put on their rows, `index.ts` carries it into the `providerSettings` account rows,
the settings model list prints each account's own marker beside that account's pool checkbox on
the model row, and `modelRowLabel` renders the marker for any row whose own source stated one —
both through the localized `modelsDisabled` copy. The harness `LlmModelInfo`
contract has no such field, so the plugin owns the extension and must route every reader through
`modelDisabledReason` rather than re-casting.

The session model picker is not one of those surfaces. It belongs to the harness client, reads the
model catalog RPC, and its `LlmModelInfo` / `ModelCatalogModel` carry no disabled marker, so a
provider-disabled model still appears there as an ordinary selectable row. Making that picker state
the condition is a harness-side change — the model-info contract, the catalog projection, the
picker component, and its locale dictionaries — and is not made from this subtree.

**Preservation rule.** Re-apply the delegation after an upstream import, which would otherwise
restore six copies; keep `clearAccountCatalog` and `resolveOwnModel` as real prototype methods
on the adapters, because `test/provider-settings-rpc.spec.ts` patches
`CodexAdapter.prototype.resolveOwnModel`, `listOwnModels` and `supportsFastTier`, and
`test/catalog-resolution-cost.spec.ts` patches `resolveOwnCatalog` / `listOwnModels`; and keep the
provider-disabled reason on the `providerSettings` account rows, because a
row that loses it reads as an ordinary selectable model. Re-measure the duplication ratchet after
any change here: `package.json`'s `duplication` script holds `packages`/`scripts` at zero and the
plugin path at a threshold just above what remains. Measured on this jscpd build with this config,
the duplicated-lines percentage in the report is the signal: `--threshold` alone does not change
the exit code (any clone exits with the config's `exitCode: 1`, a clone-free run exits 0), so the
script's `--exit-code 0` is what keeps the documented run green.

### Subscription account concurrency and 429 policy

A pool member is one subscription account, and the service meters it as a whole. `pool-gate.ts`
owns those shared facts and `pool.ts` owns the session-to-account affinity; together they enforce:

- one account serves at most `pool.concurrency.maxSessionsPerAccount` sessions (default 2), a
  session sends one request at a time, and the next session waits in FIFO order for a slot;
- one shared account request limiter (token bucket `requestsPerMinute` = 20 with `burst` = 2, plus
  `minGapMs` = 1500 ms) applies to every session of the account and is active by default;
- an ordinary 429 backs off only the session that received it, using the provider's disclosed wait
  when it sent one, and never moves the request to a sibling account; `backoff.maxRetries` = 10
  consecutive backoffs end the turn's retry budget (a hard-stopped `rate_limited`), and the next
  turn starts a fresh one;
- a window/quota 429, an account-level refusal and a revoked credential park the account until
  the disclosed reset, which every session sees;
- a session keeps its bound account across turns; a rematch happens only at a `turn/start`
  boundary, only because the bound account is exhausted or parked, and at most once per turn;
  with no healthy account the pool reports `NO_AVAILABLE_ACCOUNT` and contacts nothing.

The gate consumes the taxonomy classified in `pool-health.ts`; producers live in
`common.ts`/`claude-failure.ts`:

| Class | Producer | Effect |
|---|---|---|
| Transient | 408, 409 (`CONFLICT`), ordinary 429, 500/502/503/504/529, `TRANSPORT`, `TIMEOUT`, pre-delivery `MALFORMED_RESPONSE` | `session-backoff` |
| Account cooldown | 429 window/quota (`ENFORCEMENT` on a 429), account-shaped 403 (`ENFORCEMENT` on a 403: stated-final, billing/credits, disabled account), `QUOTA` | `account-cooldown` |
| Refresh | 401 `AUTH`, revoked-wording 403 `AUTH` | `refresh` (parked after `maxRefreshAttempts` = 2) |
| Model-scoped | model-wording 403/404 (`MODEL_DENIED`), unnamed 404 (`HTTP_404`) | `model-scoped` |
| Terminal | 400 `INVALID_REQUEST`, 413, version/policy/content refusals, `ABORTED`, post-delivery malformed, non-403/429 `x-should-retry: false` | `throw` |
| Member-ineligible | `NO_ADAPTER` from the account-policy seam | `member-ineligible` (no request was sent) |

`403 modelDenied` now has a real producer: a 403/404 body (bounded) whose text names one model —
`model_not_found`-style codes or `model … does not exist / no access / not permitted` wording —
classifies as `MODEL_DENIED`, and the Claude route does the same for an in-band error naming a
model. A plain 403 that staffs no revoked wording stays `PERMISSION_DENIED` (terminal); a 403
naming a revoked credential/account becomes `AUTH` (refresh).

**Preservation rule.** Do not reintroduce pre-output failover for provider failures, an account
switch inside a turn, or a per-request-only concurrency limit. Keep `switchMargin` out of the
pool config and out of selection: proactive re-ranking across turns spreads one conversation over
several accounts. Keep the gate's account cooldowns in the shared `PoolHealthRegistry`, because
the Settings card and the scheduler must state the same fact. `SessionTurns` must key each
`turn/start` afresh: the session log's turn counter restarts on resume. Keep the 429 rule absolute:
no class may replay a 429 on a sibling account; `dsh-llm-retry` only retries the same account.

**Focused verification.** `test/pool-failure-table.spec.ts` is the table-driven producer × class ×
effect matrix (shared HTTP, Claude HTTP, in-band `error.type`, network/TLS/timeout/abort, malformed
before/after delivery). `test/pool-gate.spec.ts` covers slots, serialization, the shared limiter
and its defaults, per-session backoff and retry budget, refresh accounting, cooldowns, the bound
turn identity and the bounded queues. `test/pool.spec.ts` covers two concurrent sessions, the
queued third session, one request per session, ordinary-429 isolation, window-429 cooldown plus
one-rematch-per-turn, refresh-then-park behaviour, the typed `no_available_account`, and the
local-exclusion yield. `test/pool-health.spec.ts` pins the failure effects.

### Wire fidelity, stream errors, and the store lock

Five contracts the pinned wire and the credential lock depend on:

- **Temperature is forwarded, stop is refused.** A caller-set `temperature` reaches the body
  (absent leaves the library's own value); a non-empty `stop` rejects with `INVALID_REQUEST`
  before assembly, because the pinned request shape has no stop-sequence field. The genuine
  client's main-session body carries a temperature and no stop field at all.
- **A truncated stream is a transport failure.** A body that ends before its terminal event
  raises `TRANSPORT`, which the harness retries on the same account; the
  genuine client calls the same condition a dropped connection and retries it. `MALFORMED_RESPONSE`
  is retryable on these routes through `subscriptionRetryPolicy`.
- **The credential lock renews its lease.** A held lock touches its own directory every half
  stale interval, and a lock whose lease expired is removed before the waiter retries, so a dead
  holder never blocks a write and live work is never preempted mid-flight.
- **The registered route reports the wrapped adapter's identity.** `AccountPreferencesAdapter`
  delegates `providerInfo`, so each route's display name reaches the model picker instead of the
  raw route id.
- **An account key derived from the refresh token is replaced once and stays replaced.** A stored
  key with the `token-` prefix is never served: `src/auth/store.ts` replaces it with the random
  `account-<16 hex>` id the session carries (minting one only when the session has none), stores
  that id with the session, and keeps the old key as an alias. The replacement reaches the browser
  and the account-scoped state, and it is local metadata only — it is never a Claude API field.
  The write-back runs inside the store's own serialization and re-reads under the store lock, so
  concurrent reads (the status endpoint reads every provider at once) all adopt the first minted
  key instead of each minting its own and overwriting the file with it.

**Preservation rule.** Keep every one of these on the plugin side: the harness's retryable-code
set, its provider-info contract, and the client's own lock protocol are the references. Do not
add a fallback that hides a refusal (a replayed reasoning item a gateway rejects must surface),
and do not reintroduce a lock that never removes an abandoned one. Keep the account key
token-independent, persist the minted id with the session, and keep the rekey write inside the
store's serialization; a rekey that writes outside it changes the key on the next mount.

**Focused verification.** `test/claude-wire.spec.ts` (temperature/stop), `test/translate.spec.ts`
and `test/chat-completions.spec.ts` (stream classification), `test/store-lock.spec.ts` (lease and
takeover, run repeatedly because it is concurrent), `test/account-preferences.spec.ts`
(identity delegation), `test/store.spec.ts` (concurrent reads mint one durable key; a carried
`accountKeyId` outlives a token-derived key) and `test/rpc.spec.ts` (two mounts report the same
persisted key).

### Removed upstream indirection

Five pieces of upstream code were removed here and must not come back through an upstream
import; each was proven to add nothing before it was deleted.

- The Claude `/fast` description wrapper (a module whose body only called the locale getter it
  was handed). The command's description is now the locale call itself.
- The unused disposer `registerWithAlias` returned. Registration is still an effect through the
  tool registry; only the field nobody read is gone, and the function returns the resolved name
  its callers use for the per-agent deny list.
- The defensive `structuredClone` in `provider-settings.get()`. `set()` already writes a fresh
  tree, and every caller only reads; the contract is now stated in the accessor's JSDoc.
- The `pool.autoFamilies` alias, its schema entry, and the two fallbacks that read it. The
  fallbacks were unreachable (the sibling field defaults to true), so removing them preserves
  behaviour even for a configuration that set the alias.
- The unscoped `modelDefaults` read endpoint and its `ModelDefaultView` /
  `ModelDefaultsCatalog` payload types. Effort defaults are written by `setModelDefault` and read
  with the `providerSettings` reply, so one settings read serves the editor;
  `test/model-defaults-rpc.spec.ts` keeps the three writer cases and an absence case for the
  removed endpoint.

Do not hand-roll `anthropic-beta`, the billing block, `x-app`, or cache markers again.

  **Preservation rule.** Keep the derivation in the profile read (`claude-model-limits.ts` owns the catalogue key, marker included) rather than on `DiscoveredModel`, and keep a level the model does not carry off the request: the pinned builder answers `INVALID_EFFORT` when one is sent, and the harness refuses it earlier only while the advertised set is right. - Header names go out in the client's own mixed casing, because the runtime that performs the fetch preserves it and the request is identified partly by those bytes: `Accept`, `Authorization`, `User-Agent`, `X-Claude-Code-Session-Id`, and the `X-Stainless-*` platform block are title-cased, while `anthropic-beta`, `anthropic-version`, `content-type`, `x-app`, `x-client-request-id`, `x-claude-code-prompt-id`, and `x-claude-code-request-class` are lower-cased. Nothing downstream may route the plan through a `Headers`: `src/transport/bridge.ts` frames the caller's names verbatim, and `src/transport/bun-child.ts` compares its own runtime-version field case-insensitively before replacing it.
- Header plan: `x-claude-code-prompt-id` carries the same value the billing block's `cc_prompt_id` carries, under the same UUID guard, and `x-claude-code-request-class` states the class the client derives from its query source. `GenerateOptions.requestClass` outranks purpose: an explicit `main`, `compaction`, `auxiliary` or `subagent` class is reported verbatim; otherwise the purpose maps `compaction` and `session-title` to `compaction` and `auxiliary`, and everything else is `main`.
- Identity: `deviceId` and `accountUuid` come from the stored `ClaudeSession` (the account UUID is discovered at login, preserved across refresh and lazily backfilled for pre-upgrade sessions; a failed backfill fails the request with `INVALID_REQUEST` instead of sending a bogus triple). `deviceId` is a 64-hex derived value, the format the genuine client uses, never a random UUID: `deriveAccountDeviceId` hashes the account key together with this machine's own operating-system identifier, so the same account on the same installation rebuilds the same id with no cache, and a host exposing no usable identifier fails with `CLAUDE_DEVICE_IDENTITY_UNAVAILABLE` rather than falling back to an account-only or random value; the account-and-device binding section below owns the platform reads and the conditional replacement of legacy or foreign-device values. The previous request id is selected from the durable session log rather than a process-local table: the retained assistant message whose trusted metadata states the same account reference, wire session and span epoch supplies the id spliced into the next request's billing block, so a pool failover never chains another account's request id. A missing or empty request id scans backward for an eligible record, while an invalid selected non-empty id is omitted without backtracking. `cc_prompt_id` is derived deterministically from (wire session, prompt turn) by `claudePromptId`: the same session and turn always produce the same id and the same request bytes, while another session or the next turn differs. The value is model-visible, so the harness rule that anything a model sees must be reconstructable from the session log requires the derivation — a random UUID is not reconstructable. The turn's tool-continuation steps reuse it; probe/title-helper suppression is not modelled. The response's `request-id` header is recorded on that assistant message's replay envelope as `response.requestId`, the checkable counterpart of the `cc_prev_req` chain.
**Preservation rule.** Keep every started continuation-state operation owned until it really settles. Later callers wait in one FIFO queue, in arrival order, for that settlement and then each performs a fresh locked read-modify-write on the text its predecessor committed; only the caller's own cancellation (`AbortSignal`) or plugin disposal ends a wait, and elapsed time never does (`continuationStateDeadlineMs` is advisory accounting and refuses no request). A live cross-process lock holder is likewise waited out; only a lock path that cannot be created refuses. Ending a queued caller's wait starts none of its own I/O and does not cancel the preceding work. Disposal admits no new work and awaits owned work. [test/claude-salt-store.spec.ts](test/claude-salt-store.spec.ts) owns this path.
- The session identity is a UUID in both places the client declares it, `X-Claude-Code-Session-Id` and `metadata.user_id.session_id`, and `buildClaudeWireRequest` refuses a wire session id that is not UUID-shaped. The harness session id is the durable key that identity is selected by, never a value on the wire: it is `session-<uuid>`, which no genuine client sends. Each account span of a harness session carries its own durable wire id in the private span document, so one conversation never spans two account identities; switching back selects the original id and chain from the log again.
- The system prompt has exactly one carrier. When the loop supplied `systemSections`, those sections are it: the leading system-role message of the derived history holds the same rendered prompt, and lifting it into the `system` array would both send the prompt twice and put the unfiltered `harness:identity` text and the machine-local `harness:source` checkout path on the wire. A request without sections still passes `options.system` and the history's leading system text through `toAnthropicSystem`.
- `HARNESS_LOCAL_SECTIONS` names the harness-owned sections a client-shaped request never carries: `harness:source` (the checkout path) and `app:web-surface` (the harness's Web GUI name, its `127.0.0.1` endpoint, and that GUI's dev-server contract). Both describe this deployment rather than the client the request claims to be. `harness:identity` is deliberately not in the set: the harness already exposes `includeHarnessIdentity` and a deployment persona for it, so this route replaces that section with its own line rather than dropping it.
  **Preservation rule.** Keep the set keyed by section name with both entries, and keep the spec's fixture built from the live section texts. The owner's request reproduced the whole `app:web-surface` section, which the model answered by naming the harness GUI, and a fixture carrying only synthetic sections cannot catch the next section like it. A harness section that names the product, a local endpoint, or the GUI belongs in this set and in `test/claude-wire.spec.ts`.
- Wire-builder rejections map through `mapClaudeWireError` to `INVALID_REQUEST` errors naming the wire code (`INVALID_EFFORT`, `INVALID_THINKING`, `UNSUPPORTED_CAPABILITY`, `CRYPTO_UNAVAILABLE`, `INVALID_IDENTITY`, `INVALID_UNICODE`, and the rest by default); `INPUT_TOO_LARGE` alone goes through the offload path. ### Claude transport request lifetime

### Claude failure classification and hard stop

`src/providers/claude-failure.ts` owns the one ordered classification for this route: a client-version refusal first, then a refusal the provider states is final, then credential expiry, a releasable quota window, a request fault, a recognized transient failure, and last an unclassified error. A failed status and an `error` event inside a `200` run the same order, and the result is a value — `reason`, `serverCode?`, `status?`, `stage`, `scope`, `retryDisposition`, `outputDelivered`, `retryAfterMs?`, `origin`, `protocolFingerprint` — that callers act on. **Preservation rule.** Keep the classification ordered and the allow-list closed: give no unlisted code a default of permission, keep a 403 out of the credential path, and keep the hard stop independent of listener registration order. ### Claude account maintenance for live sessions

`src/providers/claude-maintenance.ts` owns credential renewal, profile freshness and the managed-settings read, and `src/providers/claude-account-state.ts` owns the pure vocabulary and the validated `claudeMaintenance` configuration. A binding exists only after `ensureReady` served a real request that named a harness session; the adapter's `beforeAccountRequest` hook awaits the hydration of stored state before judging anything, and a stream ending, an idle turn or a finished response is not a release — only session disposal, a user stop, a logout or an account removal releases, and that release quiesces the work the session owned without cancelling another session's shared work. A request with no session still gets its credential and policy checks but creates no continuing session binding or timer, though a safe result may still be cached durably. Freshness, completeness and eligibility are decided from values: a profile is fresh for `profileMaxAgeMs` with the baseline itself already stale, adopted only with `account.uuid`, `account.email` and `organization.uuid`, and complete only on the reader's evidence — `organization.billing_type` stated, `account.created_at` present, `organization.subscription_created_at` stated, and `cc_onboarding_flags` present with an absent object counting as `{}`; the subscription type is outside that test (an explicit `null` counts as stated, and an absent property never erases a known value), a record without `completenessVersion` reads as incomplete and one bounded read replaces it while the policy state beside it is kept, and the managed-settings fetch runs only for a first-party OAuth account that is not a confirmed `pro`/`max` and is either an organization subscription or unknown. A restored maintenance record states a pin only when its own projection is its whole document — the endpoint's empty success, a 204/404 stored with an empty checksum and revision, no key, no blocker and nothing enforced (`enforced: false`) — and that record restores as a verified empty policy, adding no settings or organization call on its first use while the ordinary cadence is unchanged. Every other restored record, including a non-empty summary whose full body this process does not hold and a record that only looks empty, states no pin, so the checker refuses the account until an eligible bound account's next real request performs one bounded, unconditional full read that sends no validator and can therefore never be satisfied by a 304; a confirmed `pro`/`max` account still reads nothing and keeps the restriction unknown. A genuine organization mismatch stays a hard stop (`POLICY_ORG_PIN_REFUSED`). The settings read carries its own role headers — plain `claude-code/2.1.288` user agent, the `oauth-2025-04-20` beta, and both `cache-control: no-cache` and `pragma: no-cache` — under its own ten-second deadline, which the token bound does not cover. `assertAllowed` fails closed: an untrusted durable state, an identity conflict, a refused profile, an unvalidatable document, an unsupported or unmapped key, and a restriction whose consumer is missing all deny; the tool guard in `index.ts` reads the live policy at execution time for the accounts that session actually routed to, and asks for every scope conservatively.

A token-endpoint POST — the authorization-code grant or the refresh — runs through one helper bounded at 30 seconds for the whole exchange: the fetch plus reading and parsing the answer, a success document or an error body, not only the response headers, with the deadline cleared after the consumer returns. A POST past the bound is aborted and reported as `TIMEOUT` whose cause is this plugin's own expiry error rather than the endpoint body; the helper does not replay the grant, and a timeout is not a permanent refresh failure, so it leaves the stored credential in place. No refresh outcome deletes an account: a permanent refusal parks it as `reauth_required`, and only an explicit logout removes it. The transport applies no deadline of its own, and the bound is a wall-clock deadline on the components it wraps rather than a claim that every adapter's timeout is equivalent.

**Preservation rule.** Keep maintenance demand-driven: no status, catalog or badge read may create a binding, start a timer or reach a provider, and no bound-work release may cancel work a live session still needs. Keep a restored record's pin tied to its own whole document: only the exact empty-success tuple (empty checksum and revision, no key, no blocker, `enforced: false`) restores with no added settings or organization call, every other restored record states no pin and is read in full once by an eligible bound account without a validator so an unsolicited 304 can never validate it, and a genuine organization mismatch stays a hard stop. ### Credential preservation in the auth store

Files: `src/auth/store.ts`, `test/store.spec.ts`, `test/store-preservation.spec.ts`.

`auth.json` holds bearer credentials. Its invariant is that a provider or account entry may disappear only through an explicit `deleteAccountSession` (the Settings logout). A read, a status fan-out, a refresh, a migration, a rekey, or any unrelated write must retain every entry the file holds, including entries this build cannot parse:

- `parseStore` keeps skipped provider and account entries in a `StorePreservation` attached to the parsed store (a `WeakMap`, so no typed field leaks into the session API). That covers a non-object provider value, a single-account record without usable tokens, a hybrid bare-session-plus-accounts entry, a missing or non-object accounts map, a non-string `default`, and account entries missing tokens or stating an unknown Claude ownership mode.
- The writer rebuilds the document from the raw parse, merges typed entries over it, restores skipped accounts where they were, copies unknown top-level keys verbatim, and keeps unknown revision maps. A Codex rekey records the retired key as an alias, so the raw key's absence is a move rather than a loss; a canonical key that already holds a session makes the rekey leave the record under its stored key instead of deleting one of the two credentials.
- `writeStore` refuses before touching the file when a raw provider value cannot coexist with a typed entry (a scalar or a tokenless single-account record that would gain an accounts map), when the merge would omit an account with no removal marker, or when the new document would shrink the current file without the explicit-prune flag that only `deleteAccountSession` passes. Every refusal leaves the file byte-for-byte unchanged.
- Writes are temp-file + `fsync` + atomic rename. The Windows `copyFile` fallback was removed: a non-atomic overwrite could corrupt every credential in the file, so a rename that cannot complete fails instead. The previous generation is copied to `auth.json.bak` (mode 0600) before the live file is replaced; a failure to write that backup fails the whole write.
- A store lock that cannot be acquired fails the write. Degrading to an unlocked write let two processes read the same file and the later rename drop the other's account. The read-back of the pre-rename migration is verified against the legacy file before that file is removed.
- A permanent refresh failure is reported as `INVALID_CREDENTIAL` and parks the account as needing re-authentication; it never deletes the stored credential. An unpersisted rotated token is reported as `CREDENTIAL_NOT_PERSISTED` after a bounded save retry and is never answered with the pre-refresh session. A Claude refresh response that omits `scope` keeps the stored scopes.

**Focused verification.** `test/store-preservation.spec.ts` covers malformed provider/account preservation, refusal of unmergeable and shrinking writes, `.bak` contents and backup failure, a live foreign lock, the refresh-save failure, single-account migration, and explicit logout. `test/store.spec.ts` covers rekeys, collisions, and concurrent writers. `test/token-refresh-commit.spec.ts` and `test/accounts.spec.ts` pin that a permanent refresh failure deletes nothing. `test/claude-continuation-integration.spec.ts` pins the parked account through the real composition.

#### Pending-refresh journal

Path: `$DSH_HOME/plugins/subscriptions/auth.json.pending-refresh.json` — beside the store, so an explicit store path uses `<store>.pending-refresh.json`. Mode 0600, atomic temp + `fsync` + rename, serialized under its own `<journal>.lock`. Never a replacement for `auth.json`; recovery merges one account at a time.

```json
{
  "version": 1,
  "rotations": {
    "<provider>": {
      "<account>": {
        "phase": "pending | completed",
        "provider": "<provider>",
        "account": "<account>",
        "startedAt": 1710000000000,
        "updatedAt": 1710000000000,
        "priorRevision": 26,
        "priorFingerprint": "sha256:<64 hex>",
        "session": { "accessToken": "...", "refreshToken": "...", "expiresAt": 0 }
      }
    }
  }
}
```

`pending` is written before the grant request and carries only the provider/account, the prior credential revision and a SHA-256 digest over the two tokens being spent — never either token. `completed` adds the minted `session` and is written after the response, before the store save. The marker is cleared only after the store write lands; the store save also clears a stale marker because the landed credential is then authoritative. A journal that cannot be read or has an unsupported version is never replaced: the refresh is refused before spending a grant, and recovery reports it.

Recovery (startup, `recoverPendingRefreshRotations`): a completed marker is applied only while the store still holds the credential its `priorFingerprint` names, using the read revision as a compare-and-set; a marker whose session the store already holds is cleared; a marker whose account is absent is discarded so an explicit logout is never undone; a marker whose stored fingerprint matches neither prior nor journal is left in place and the account reports `reauth_required` until it is resolved. A pending-only marker has no minted credential to restore and is cleared with a warning. Recovery never deletes a stored credential.

**Focused verification.** `test/refresh-journal.spec.ts` injects a failure before the request, after the response before the journal record, after the record before the store save, and after the save before the clear; it also covers restart recovery (apply, already-satisfied, divergent, logged-out), pending-only markers, an unreadable journal, marker permissions/schema, a live journal lock, and explicit logout.

### Windows credential store

`writeStore` in `src/auth/store.ts` writes `auth.json` to a temp file, flushes it, and renames it into place. On Windows that rename returns `EPERM` when the destination is briefly locked. It is retried a bounded number of times and then the write fails, leaving the old file whole; the previous non-atomic `copyFile` fallback was removed because an interrupted copy could corrupt the only credential store.

The 0600 write mode is the owner-only guarantee on POSIX only. Windows keeps the mode byte without turning it into an ACL, so the store inherits the ACL of the directory holding it, and a harness home under a path that grants `Authenticated Users` Modify leaves the bearer tokens readable by every authenticated user of the machine. Node cannot narrow that: the fix is an ACL on the home directory (`icacls`), not a code change.

### Host-published proxy policy

Files: `src/transport/host-egress.ts`, `src/http.ts` (`proxiedFetch`), `src/transport/claude-fetch.ts`, `test/proxy-host.spec.ts`, `test/transport-wiring.spec.ts`.

A launcher that configures a proxy publishes its resolved policy into the process environment before any plugin mounts — `HTTP_PROXY` / `HTTPS_PROXY`, `NO_PROXY`, and the mandatory Claude route `DSH_CLAUDE_PROXY_URL` — and the dispatcher it installed is what applies that policy to an ordinary `fetch`. This plugin declares no dependency on the host's transport package (it lives outside the workspace, so the seam is not resolvable from its directory, and a bundled copy would read module state that is always empty), so the published environment is the honest seam:

- `proxiedFetch` attaches no dispatcher of its own to a Claude destination (`anthropic.com`, `claude.com`) while `DSH_CLAUDE_PROXY_URL` is published: the installed dispatcher applies the mandated route to Messages, token refresh, usage and profile alike, ahead of the plugin's own proxy.
- For every other destination it leaves the process dispatcher in charge whenever the host published a proxy for the request's scheme and the plugin's own proxy did not take the request, so this module's direct agent cannot carry it around that proxy. `NO_PROXY` and loopback decisions stay the installed dispatcher's rather than a second matcher here.
- The plugin's own proxy and its bypass list still decide the requests they cover, and when the host published nothing the plugin's direct agent (which carries the module's connect budget) is attached to the remaining ones as before.
- The Bun bridge refuses the Messages request with `BridgeUnavailableError` naming the variable and its credential-free origin, before the child is resolved or spawned. The child runs its own runtime and its environment allowlist carries no such variable, so a bridge that took the request would send it outside the route. `DSH_SUBSCRIPTIONS_BRIDGE=off` is the offered remedy and stays inside the route, because the fallback path defers to the host dispatcher as described above.

**Preservation rule.** An upstream import restores none of this. Keep `host-egress.ts`, the three decision points above, and the refusal ahead of `startBridge`. Importing the host's own seam (`proxyRouteFor` / `proxyEnvironmentForChild`) is deliberately not taken: the package is not resolvable from this plugin's directory, and declaring it would mean making the plugin a workspace member. Bridge proxy support, which would let the bridge carry the route instead of refusing it, stays deferred until Bun's proxy-environment behavior is measured and `Config` gains its switch.

**Verification.** `test/proxy-host.spec.ts` proves the deferral on both Claude hosts and on a published general route, that the plugin route and its own direct agent survive when nothing is published, that a refusal names no proxy credential, and that an enabled plugin proxy still carries other providers; `test/transport-wiring.spec.ts` proves the refusal precedes the child and that the child environment never receives the variable.

### Speed control

The composer's model menu Speed row, the `/fast` popup and the Settings model list write one durable tier per provider model, held as the `speed` section of `model-defaults.json` beside the per-model effort defaults (`src/model-defaults.ts`: `defaultSpeedOf` / `setDefaultSpeed`, one write chain shared with `setDefaultEffort`, `standard` clearing the entry). A new session, a restart and a plugin reload all read a stored tier back, so standard routing is the absence of an entry rather than a per-process default; the row resolves the session's current model and addresses that entry, and the request side reads it synchronously. The tier reaches only the three routes whose catalogs carry a per-model fast tier, each through `speedFor(model)`, and each adapter applies it only where its own catalog advertises the tier:

- Codex reads `service_tiers`/`additional_speed_tiers` from the live catalog (discovery-gated, so a route with `discovery: false` claims no fast models at all) and sends `service_tier: priority`.
- Cursor reads the catalog's `fast` parameter.
- Claude reads the pinned profile's `fast_mode` catalogue string through `claudeCatalogueEntry`, exactly as `claudeReasoning` and `claudeThinkingType` read the same profile for effort, so its fast models need no discovery read.

A stored `fast` the model cannot honour — a hand-edited file naming a plain model, or a catalog that stopped advertising the tier — stays stored and inert: `CodexAdapter.request`, `CursorAdapter.streamOwn` and `ClaudeAdapter.request` each short-circuit on their own capability before the wire field is built. `ClaudeAdapter.request` passes the surviving tier to `buildClaudeWireRequest`, and `claudeSpeedField` emits `speed: 'fast'` or omits the field: Standard is the field's absence, never a `"standard"` literal. The pinned builder pushes `fast-mode-2026-02-01` from that same field inside `composeBetas`, so nothing else on this route may name the beta or pass it as an additional beta — one field, one composition.

`SpeedSelect` renders the composer's one Speed control: a row contributed to the model menu, under the seat's model and effort cells. It registers into `conversation.input.model.row`, the additive child slot the `conversation.input.model` seat declares in `packages/client/ui-model-selection` (the seat itself stays single-owner; the key is declared in `packages/client/ui-conversation`'s contract, which is why the plugin needs no new dependency). The row's root cell carries its key as `data-model-menu-row` and opens the tier pane through the seat's owner face (`activeRow`/`openRow`/`back`/`closeMenu`): the seat hides its own cells, keeps the row mounted — its read, in-flight write and failure strip survive the switch — and routes `↑`/`↓`, `Escape`, `Tab` and `Shift+Tab` to the pane, which is the card's single scroll region, so the Standard/Fast choices stay inside the card's own bounds. A row that hides itself while its pane is shown calls `back`, and a write that settles after the pane was left or replaced closes nothing. It decides visibility from `FAST_TIER_PROVIDERS` and the node half's fast-capable listing (`speedControlVisible`), and stamps every read of the host state with the choice generation it started under (`settleRead`/`settleChoice`). The read asks the node half to enumerate fast models and the host for the session's model, so it is slower than the write it can race: without the stamp a read started before a choice settles after it and puts the replaced tier back on screen. The Settings model list reads the same store, and a row carries `fastTier` so the picker appears exactly where a chosen fast can reach the wire. A `speed` RPC enumerates only its requested provider, and the client skips that RPC for providers without a speed control; unrelated provider discovery must not delay the control.

**Preservation rule.** Keep the tier durable and keyed by provider model, in one document with the effort defaults and behind one write chain. Keep the speed read provider-scoped and the client provider check before the RPC; `test/speed-control.spec.ts` rejects both cross-provider enumeration and RPCs for unsupported providers. Keep each route's `supportsFastTier` reading its own source — the pinned profile for Claude, the live catalog for Codex and Cursor — rather than a shared list, and keep the capability check inside the adapter that builds the request rather than only at the wiring, so no caller can send a tier its catalog does not advertise. Keep `speed` out of the body on Standard, and leave beta composition to the pinned builder. Keep one Speed control: the model-menu row, never a second control in the composer tool row — the chip this row replaced showed the same setting twice. Keep the harness's `conversation.input.model.row` child declaration with its owner face and the `data-model-menu-row` marker (`packages/client/ui-model-selection`'s seat registration + the contract key and `ModelMenuRowOwnerProps` in `packages/client/ui-conversation` + the `renderSlot` call with the owner props in `ModelSelect`): dropping any strand strands the row, and a cell without the marker leaves the seat no target for the keyboard it returns. ## Verification and packaging

Build the Harness from the repository root first with `pnpm run build`. The fork compiler resolves the LLM and attachment declarations from that build; `test/isolate-home.mjs` selects the repository TypeScript paths before the ESM-only test hook loads.

## Deployment

The live Web profile pins the plugin through a `file:` reference to the tarball in `fork-plugins/releases/`; the credential store lives separately under `DSH_HOME\plugins\subscriptions\` and must never be touched by a code swap. The plugin's own `@tormentalabs/claude-code-wire-compat` dependency must keep the absolute `file:C:/Project/deepseek-harness/fork-plugins/releases/tormentalabs-claude-code-wire-compat-0.7.2-dsh15.tgz` specifier in the packed `package.json`: pnpm resolves a dependency's nested `file:` specifier relative to the installing profile, not to the plugin directory, so `file:../releases/...` made the artifact fail to install with `ENOENT` on `<profiles>\releases\...`. Deploy by stopping the Host, then running `fork-plugins/deploy-subscriptions-web.ps1` from a plain PowerShell window with an explicit `-Version` argument (sha256-verifies the artifact, refuses while the Host listens on port 3080, backs up the installed copy plus `package.json`/`pnpm-lock.yaml`, and swaps through `pnpm add` so a later `pnpm install` cannot downgrade). Restart the Host with its usual launch command. Rollback follows the rules under [Rollback](#rollback) rather than an assumed previous tarball.

**macOS install limitation.** That same absolute specifier is what lets the artifact install for the consumer, and it is a Windows drive-letter path. The macOS leg of `setup.command` therefore cannot install this plugin as it stands: the profile's install resolves the nested pin against itself and finds no `C:\...` target. The plugin serves the Windows Web profile; macOS support is out of scope by the owner's decision, and the limitation is recorded here rather than worked around. Making both legs work means shipping the wire package inside the plugin package (`bundledDependencies`) instead of referencing a tarball, which changes the release layout and is not done.

## Updating upstream

Import an exact reviewed tag through the subtree, reapply the RC.1 cohort and lifecycle adaptations, then reapply every item under "Reapply after an upstream import" above. Run the package suite, advance the private version, and rebuild the fixed artifact. Never install npm `@latest` directly into the live profile.

## Rollback

Rollback changes only the pinned package and profile configuration after DSH stops. Preserve the plugin credential store and do not rewrite Session, attachment, or provider-account data. Older code reading JSON is not a reason to roll back: the new `llm/request-record` reader and every log written with it are kept, and a rotated token is never replaced by a restored auth snapshot. When no compatible rollback artifact exists, the permitted exit is disabling the Claude route or the plugin after the privately rehearsed safe exit, which has passed against the real packed candidate and keeps the new logs and the rotated credentials instead of restoring a credential snapshot. The retained previous release, `fork-plugins/releases/dsh-plugin-subscriptions-0.9.4-dsh017rc1.29.tgz`, and every other tarball stay in `fork-plugins/releases/`: never repack or delete a released tarball to make room.
