# Agent Note: 头部清单不计算历史全库修订号

Status: implemented

[English](2026-10-31-header-listing-skips-corpus-revision.md) | 中文

## 问题

工作区启动时通过 `sessionPersistence.list()` 为每个已存储会话建立头部索引。历史 JSONL 产物的修订号会折入持久化根目录下所有所选 generation 的一次指纹，因为其逻辑事件要用子智能体子项补齐父目录。因此，当存储中归档了许多历史父会话时，启动会为根目录下每个会话付出一次目录读取与一次 generation stat，尽管头部索引从不比较修订号。冷标题折叠有同样的形态：它不使用调用方的排除项去列出语料，并请求了从未读取的快照修订号。

## 决策

持久化接缝暴露 `listHeaders(options)`。它选出的集合与 `list` 完全相同——同样的排除项、同样包含已创建但未实体化的会话、同样不承诺顺序——并返回每个会话的 `header` 与 `formatStatus`，不返回修订号。JSONL 后端用与 `list` 相同的共享元数据扫描来服务它，并跳过全库指纹；`list` 与 `stat` 保留该指纹。修订号本身低开销的后端继承默认实现：委托 `list` 并丢弃修订号。

`WorkspaceRegistry` 通过 `listHeaders` 建立启动与 attach 校验所用的头部索引。`SessionQuery` 同样只拉取已存储头部，`readTitleSnapshots` 接受调用方的列表排除项，使冷标题回填不再列出可见列表已经隐藏的归档与子智能体行。

## 考虑过的替代方案

**启动时不为任何归档会话建立索引。** 有记录归属的归档成员仍属于工作区记账，成员资格由 `candidateMatches` 与 `reportFilteredCandidates` 依据已校验头部决定。放弃索引会使它们从 `sessionIds` 中消失、改变过滤告警，或需要一种保留归属但不做校验的延迟记账状态。实测成本来自全库指纹，而不是这些归档头部本身。

**给 `list` 增加一个选项，把历史修订号收窄到 generation 文件。** 这样返回的令牌的含义就会少于 `list` 约定所承诺的内容，后续调用方可能据此缓存派生的逻辑事件。新增一个根本无法返回修订号的方法可以消除这种误用。

**把指纹收窄到每个历史父会话的子项，或在进程内复用。** 子项只能通过扫描全库或信任持久化 catalog 来发现，而 catalog 条目可能已被其他进程淘汰；进程内复用也无法证明外部写者没有新增子项。保守的全库指纹保留。

## 后果

启动只触碰列表所选的会话目录，只取头部的调用方不再承担全库扫描。接缝增加一个方法，且所有后端的选择集合保持一致：默认实现以 `list` 的代价提供它。历史 `stat` 与 `list` 修订号仍是全库且保守的，因此打开历史会话仍会付出该扫描，无关产物变化仍会使其修订号失效。
